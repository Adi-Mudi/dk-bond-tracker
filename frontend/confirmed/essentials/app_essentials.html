1 State Management — where the app keeps data while it runs

While the app is open, it must remember things. State = all remembered values. State management = rules for where each memory lives and who can read it. Two scopes only: local and app-wide.

Local state — one component only

  • Belongs to ONE widget No other screen reads it
  • Destroyed with the widget No cleanup plan needed
  • Examples: dropdown open · text in a field · chip tapped · accordion open · switch toggled
  • Tool: setState() Built into Flutter — zero packages

App-wide state — shared across pages

  • Many pages read it Bond list: Portfolio + Watchlist + Payouts
  • Outlives screens Survives navigation
  • Examples: logged-in user · bond cache · theme · privacy mask · sync status
  • Tools: Riverpod (recommended) · Provider · Bloc

Decision rule — one question settles it

"Would a SECOND screen ever need this value?"
NO → keep it local Dropdown open? Text typed? Chip selected? Switch position?
Lives inside the widget. No package. No plan. tool: setState()
YES → promote to app-wide Bond cache? Theme? Privacy mask? Sync status? Alerts?
Lives in the shared store; every reader updates automatically. tool: Riverpod (recommended)

Golden rule: local state is NOT in the app-wide plan. Every promoted item costs boilerplate + debugging complexity — the bar is a second reader, not "might be useful someday".

Guards & deep links — the special entry rules

5 API Calls — how the app talks to the back end

One client, one URL, one checkpoint for tokens/logging/retry, timeouts everywhere, one offline policy — and raw network code only ever lives in repository classes. Tool: Dio.

Visual · Where network code lives — the only legal path

Widget / Pagenever sees a URL or Dio
ViewModel / Stateasks repository, holds result
Repository (per domain: bonds, users, payments)raw JSON → typed objects or meaningful errors
⇄ INTERCEPTOR GATE ⇄stamps auth token · logging · retry — automatically on every request
Dio instance #1 — base address written ONCEhttps://api…/v1 · connect + receive timeouts set here
Servervalidates again — the last guard

50 call sites never hand-write headers — the gate stamps every request once

Timeouts — fail fast

  • Connect timeout + receive timeout set once on the Dio instance
  • "A spinner that never resolves is a bug, not a loading state" dead network → quick fail → offline UI takes over
  • Links to your 4 fetch states Checking must always reach Offline / Not Found

Error & offline policy — decided once

  • Clear offline message · retry button · never a blank screen
  • One shared handler, not per-endpoint code your designed offline copy is the spec
  • Expired token → interceptor refreshes silently, pending requests retried future slot — local-first today
