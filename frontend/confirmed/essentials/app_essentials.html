While the app is open, it must remember things. State = all remembered values. State management = rules for where each memory lives and who can read it. Two scopes only: local and app-wide.

Local state — one component only

  • Belongs to ONE widget No other screen reads it
  • Destroyed with the widget No cleanup plan needed
  • Examples: dropdown open · text in a field · chip tapped · accordion open · switch toggled
  • Tool: setState() Built into Flutter — zero packages

App-wide state — shared across pages

  • Many pages read it Bond list: Portfolio + Watchlist + Payouts
  • Outlives screens Survives navigation
  • Examples: logged-in user · bond cache · theme · privacy mask · sync status
  • Tools: Riverpod (recommended) · Provider · Bloc

Decision rule — one question settles it

"Would a SECOND screen ever need this value?"
NO → keep it local Dropdown open? Text typed? Chip selected? Switch position?
Lives inside the widget. No package. No plan. tool: setState()
YES → promote to app-wide Bond cache? Theme? Privacy mask? Sync status? Alerts?
Lives in the shared store; every reader updates automatically. tool: Riverpod (recommended)

Golden rule: local state is NOT in the app-wide plan. Every promoted item costs boilerplate + debugging complexity — the bar is a second reader, not "might be useful someday".

14 Action Feedback — telling the user what just happened

After every action the app answers: what happened. Silent success → double-taps and confusion. Message style, weight and timing decided once, same on every screen. Pairs with Motion (the press) and Forms (the lock).

Part 1 · The weight ladder — lightest that does the job

Toast / Snackbar small, reversible completions · auto-dismiss 3–5s · no user action "Payment saved"
Snackbar + Undo has a consequence or an undo option "Entry removed — Undo"
Dialog irreversible / high-risk — before or after · never for small reversible things type-ISIN + hold confirm ✓

Part 2 · Snackbar rules — one line, specific, never an error

✓ Right

  • One line, about the operation just done
  • Specific: "Entry removed" — not "Done"
  • Never the ONLY path to a core feature or important undo (2 actions → use dialog)

✗ Wrong

  • "Done" / "Success" / "OK" — vague
  • Error text in a vanishing toast
  • Toast hiding the only undo of something important

Part 3 · Undo vs confirm — your mapping

ActionKindFeedback
Save payment / edit notereversibletoast "Payment saved" — no dialog, never confirm
Remove from watchlistirreversible + high-riskconfirm BEFORE — typed ISIN + hold 2s ✓ (undo alone not enough)
Dismiss alertsmall reversibletoast + Undo ("Alert dismissed — Undo")
Move to Portfolioreversible-ishsnackbar "Moved to Portfolio"

Undo beats confirmation for reversible actions (faster, less disruptive). Never confirm a non-destructive action.

Part 4 · Errors are separate — never a vanishing toast

✓ Success = toast (auto-hides)
Payment saved✓

Gone in 3–5s — fine, nothing left to do

✗ Error = STAYS until dismissed
Could not save: no connectionRetry

Persistent · specific failure · icon+text+colour (never colour alone) · "Something went wrong" ✗
